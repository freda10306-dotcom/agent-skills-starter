# 專案種子簡報（v1）— InsightDock

> **這是什麼**：5 題問卷產出的專案 baseline，承載「目標受眾 / 痛點 / 期望成果 / 約束 / 指標」5 段。
>
> **怎麼用**：後續 15 張卡的 trigger「上游文件」貼位區，若該卡的上游 deliverable 還沒做（例如還沒寫 JTBD 就要做 PRD），可從本檔對應段落取用代替，**但必須在 AI 自檢時誠實標 `[L]` confidence + `（依據：brief §段名）` + 列為 highest-value next input**。
>
> **不能做的事**：brief **不能取代**訪談逐字稿、JTBD 文件、PRD 等更具體的下游產出。當對應上游卡完成後，下游卡的 trigger 上游貼位應改用該卡的真實 markdown 輸出，而非繼續用 brief。

## 目標受眾

UX/UI 團隊中執行使用者訪談的主訪、副訪／觀察員與產品經理；決策者或客戶也需要一起查看、協作。

## 待解痛點

問題1: 訪談執行時一心多用 => 主訪腦中同時要傾聽與理解、觀察非語言訊號、對照訪談大綱、構思追問、控制時間節奏、記錄重點，導致受訪者感覺沒被傾聽、錯失語氣與情緒等線索、只能照本宣科、團隊各記各的事後難對齊。
問題2: 訪談後整理耗時 => 一小時訪談產生數千字逐字稿，即使用 AI 轉寫仍要花大量心力修正專有名詞與錯字；沒有立刻整理，幾天後就忘了脈絡；要從逐字稿撈出金句，瑣碎又痛苦。
問題3: 資料分析難以收斂 => 面對大量逐字稿、音檔與筆記容易失焦；切片、編碼與親和圖分類全靠人工；容易只挑符合預設觀點的內容（確認偏誤）；過去的訪談躺在雲端硬碟，無法跨專案搜尋與重複利用。

## 期望成果

改變1 自動逐字稿與摘要 => 錄影自動轉成逐字稿並分出說話者，摘要與話題分類每句都連回逐字稿出處，研究員確認後才算數，而不再需要人工聽打與翻找。
改變2 AI 漏問檢核 => 按下「結束訪談」前，AI 對照訪綱列出還沒問到的核心題目，由主訪決定補問或略過，而不再需要邊訪談邊自己對照大綱。
改變3 受測者隱私與權限 => 姓名、電話、身分證、Email 自動遮蔽；研究員／團隊／客戶三種權限，客戶只看結論與片段；保存期限到期自動刪除，而不再需要人工去識別化與管控分享。
改變4 預測遊戲對抗偏誤 => 訪談前團隊匿名寫下「我猜受測者會卡在…」，訪談後揭曉誰猜對，把假設先記下來，而不再只挑符合自己預設的內容。

## 主要約束

限制1 => 真實訪談資料不足，公開資料與生成的假資料不夠真實
限制2 => 中文口語轉錄困難：專有名詞、中英夾雜、多人搶話
限制3 => AI 摘要可能失真或憑空捏造
限制4 => 長音檔處理慢、模型 API 費用高
限制5 => 受測者的影像與聲音屬個資，外部取得的訪談資料數量有限且含個資，不能外流到第三方 AI
限制6 => 兩個月時程，功能容易越做越多
限制7 => 驗證對象（科技產品工作者）工作忙、難約
限制8 => 須延伸既有 1.0 Demo（React＋Supabase，含示範資料；AI 判讀目前以規則與示範資料模擬）

## 成功指標

• 串接 AI 的 InsightDock MVP（延伸 1.0 Demo）：逐字稿、說話者分離、摘要附出處
• 受測者隱私與權限：個資自動遮蔽、三種角色權限、保存期限自動刪除
• 人機協作與人性化功能：AI 漏問檢核、預測遊戲
• 評估測試集（人工標註的真實訪談）與離線評估報告
• MVP 價值驗證與易用性測試報告
• 目標指標（待組內確認）：個資遮蔽召回率 ≥ 95%、摘要出處正確率 ≥ 90%、逐字稿字錯率優於 1.0（基準待測）、漏問檢核正確率（待訂）、單場訪談整理時間比原流程少 50% 以上、SUS 易用性分數 ≥ 70
